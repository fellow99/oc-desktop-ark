# overall-spec —— 整体规格

> 技术无关的系统级规格。实现细节见 `overall-plan.md` 与各模块 `plan.md`。
> 需求基线：`docs/000-工程规划.md` v0.3；本次需求：`000-scaffold`（工程搭建）。

## 1. 系统目的与目标用户

**目的**：把 opencode（AI 编码代理）的桌面形态带到 HarmonyOS / OpenHarmony 的 PC 与平板上，作为**本机应用**运行：无需外部服务、无需浏览器内核、不依赖开发者模式。

**目标用户**：

| 角色 | 诉求 |
|---|---|
| 鸿蒙 PC / 平板开发者 | 在设备本地用自然语言驱动编码代理：读代码、改文件、跑命令、看 diff |
| 企业内网用户 | 数据不出本机；只有模型 API 出网 |
| 现有 opencode 用户 | 与桌面版同一套界面与工作流，学习成本为零 |

## 2. 核心能力（用户故事）

- 作为用户，我能在应用内**新建会话**并发送消息，看到**流式**回复，以便边写边看得懂。
- 作为用户，我能看到**工具调用**（读文件 / 改文件 / 搜索 / 执行命令）的过程与结果，以便判断代理做了什么。
- 作为用户，我能对**权限询问**（是否允许某次工具调用）作出选择，以便控制风险。
- 作为用户，我能**切换模型 / 填写 API Key**，以便使用自己的账号。
- 作为用户，我能**选择工作目录**，以便让代理在我关心的项目里工作。
- 作为用户，我**重启应用后会话仍在**，以便中断后继续。
- 作为用户，我能查看 **diff / 版本库状态**，以便确认改动。
- 作为用户，我能看到**失败的确切原因**（阶段 + 日志），而不是白屏。

## 3. 功能需求（按域）

> 编号规则：`FR-<域>-NNN`。模块级细化见 `1NN-*/spec.md` 的 `FR-1NN-NNN`。

### 3.1 启动与运行时（RUNTIME）

- **FR-RUNTIME-001**：应用 MUST 在一次启动内把 Node 运行时拉起一次，且**不创建**任何 Node 子进程。
- **FR-RUNTIME-002**：应用 MUST 以「阶段 + 结果」的形式展示启动进度（≥5 个阶段），任何失败 MUST 落到可读错误页。
- **FR-RUNTIME-003**：运行时状态 MUST 区分「已投递」与「已就绪」；只有观测到就绪证据才算成功。
- **FR-RUNTIME-004**：应用 MUST 保证单实例运行；重复启动不得产生第二个服务端或第二份数据库写入者。
- **FR-RUNTIME-005**：崩溃 MUST 被记录（信号/阶段/日志尾），并提示用户重启应用；应用 MUST NOT 假装可以原地重启运行时。

### 3.2 服务与载荷（SERVICE）

- **FR-SERVICE-001**：应用 MUST 以本机回环地址提供 HTTP 服务，并同时提供界面与接口（同源）。
- **FR-SERVICE-002**：服务端口 MUST 在运行时确定，且 MUST NOT 使用固定端口作为产品路径。
- **FR-SERVICE-003**：服务就绪后 MUST 提供一个可被宿主观测的就绪证据（文件或日志行）。
- **FR-SERVICE-004**：应用 MUST 在本地持久化会话数据；重启后数据 MUST 仍可读。
- **FR-SERVICE-005**：载荷 MUST 有完整性校验（哈希清单），校验不符 MUST 拒绝启动并说明原因。

### 3.3 渲染界面（UI）

- **FR-UI-001**：主界面 MUST 由系统 Web 组件（ArkWeb）渲染，包内 MUST NOT 携带浏览器内核。
- **FR-UI-002**：界面 MUST 与服务同源，MUST NOT 需要 CORS 配置或自定义协议。
- **FR-UI-003**：本地存储（localStorage / IndexedDB）MUST 可用；不可用时 MUST 在诊断面板说明。
- **FR-UI-004**：首屏加载前 MUST 显示应用内加载页；成功后 MUST 清理导航历史，避免返回键回到中间态。
- **FR-UI-005**：外部链接 MUST 交给系统处理，MUST NOT 在应用内打开任意网页。

### 3.4 身份与凭据（AUTH）

- **FR-AUTH-001**：服务 MUST 始终启用口令保护。
- **FR-AUTH-002**：口令 MUST 由宿主生成并跨启动稳定；宿主 MUST NOT 把口令写入日志或崩溃记录。
- **FR-AUTH-003**：界面首次加载 MUST 无需用户手工输入口令。
- **FR-AUTH-004**：口令不匹配 MUST 表现为可见的失败状态，并提供重置路径。

### 3.5 宿主能力（HOST）

- **FR-HOST-001**：应用 MUST 向服务暴露一组受控的宿主能力（权限查询、目录选择、外链、通知）。
- **FR-HOST-002**：未注册的能力调用 MUST 明确失败，MUST NOT 返回空值或崩溃。
- **FR-HOST-003**：目录访问 MUST 经用户授权；每次启动 MUST 重新确认授权有效性。

### 3.6 上游适配（UPSTREAM）

- **FR-UPSTREAM-001**：上游改动 MUST 以幂等补丁表达，且 MUST 可反向校验。
- **FR-UPSTREAM-002**：补丁集 MUST 只包含本工程必需的偏离项，并逐条记录理由。
- **FR-UPSTREAM-003**：上游版本 MUST 固定（tag + 提交），升级 MUST 走新建补丁目录。

### 3.7 合规（COMPLIANCE）

- **FR-COMPLIANCE-001**：应用 MUST 满足上架清单 G1–G11（ArkWeb 渲染、无浏览器语义、无第三方内核、许可齐备、AI 标识等）。
- **FR-COMPLIANCE-002**：受限权限 MUST 按真实需要申报，并 MUST 与使用点一一对应。
- **FR-COMPLIANCE-003**：发布构建 MUST NOT 包含调试通道（`--inspect`、探针开关、诊断端点）。

### 3.8 版本库（VCS，v1 纳入）

- **FR-VCS-001**：应用 MUST 在不依赖系统 git 的前提下提供基础版本库能力（状态 / diff / 提交 / 分支）。
- **FR-VCS-002**：凭据 MUST 存于沙箱且权限最小化；界面 MUST NOT 回显完整口令。

## 4. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 冷启动到首屏可交互 SHOULD ≤ 15 s（⬜ 待实测）；SSE 首事件 SHOULD ≤ 2 s |
| 可靠性 | 单次会话长跑 30 min 不崩溃（⬜）；崩溃可取证 |
| 体积 | 签名 HAP SHOULD ≤ 140 MB（不含用户数据） |
| 安全 | 见 `constitution.md` §三（S1–S7） |
| 可用性 | 所有失败态有中文可读文案；无空白页 |
| 可维护性 | 运行时契约只引用不复制；规格可追溯（FR → 代码 → 测试） |
| 国际化 | 界面语言由上游 UI 提供；壳层文案中文（v1） |
| 无障碍 | 依赖 ArkWeb 与上游 UI 的既有能力（v1 不额外承诺） |
| 离线 | 除模型 API 外不依赖外网；模型清单一律走内嵌快照 |

## 5. 系统边界

**在范围内**：本机服务托管、ArkWeb 渲染、凭据、宿主能力、载荷构建、版本库插件、上架合规。

**不在范围内（v1）**：手机适配、终端/PTY、MCP 外部进程、插件在线安装、后台常驻/开机自启、多窗口、跨设备同步、云端账号体系。

## 6. 验收总则

- 每条 FR 至少对应 `overall-test-cases.md` 中一个用例（`TC-*`）。
- 验收陈述必须是**可观测事实**（文件内容 / HTTP 字段 / 截图 / 哈希），不得是主观判断。
- 未在真机验证的条目必须标 `⬜ 待验证`，不得计入「已完成」。
