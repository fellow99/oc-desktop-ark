## 1. 项目概述

### 1.1 一句话定义

`oc-desktop-ark` 是一个 **ArkTS 应用**：`EntryAbility` 启动后由 `@fellow99/node-bridge` 在**应用自己的进程内**拉起 Node v24.2.0，Node 侧加载 **opencode v2.0.26 的 stock CLI 产物**并以 `serve` 语义常驻（同源托管 `/api/*` 与内嵌 Web UI）；主界面是一个 **ArkWeb `Web` 组件**，先显示应用内加载页，探活成功后 `loadUrl('http://127.0.0.1:<port>/?auth_token=…')` 加载**由本机服务渲染的**标准 opencode Web UI —— 同源、零 CORS、零 IPC 载体、零 preload 桥、包内零浏览器内核。

## 2. 背景与依据

### 2.1 三条路线，以及为什么选第三条

| 路线 | 形态 | 已证程度 | 代价 |
|---|---|---|---|
| **R-hos**（现状） | Electron 主进程跑 Node + `BrowserWindow`（Chromium）渲染 | ✅ 真机全功能跑通（`oc-desktop-hos` v2.0.26） | ① 上架 P0：**未使用 ArkWeb**（同型工程被驳回，原文见 §2.5）② 包内 181 MB `libelectron.so`，签名 HAP **250.4 MB** |
| **R-hybrid** | Electron 只作 Node 宿主 + **ArkWeb** 渲染（hos V2 的 R2） | ⬜ 未验证 | 仍随包分发 Chromium 只为一个 Node；两套运行时并存 |
| **R-ark**（本工程） | **进程内 Node（bridge）+ ArkWeb**，无 Electron | 🔶 同形态已在 `pi-desktop-ark` 跑通（`dlopen` + `node::Start` + ArkWeb） | Node 运行时约 121 MB；宿主崩溃 = 应用崩溃（进程内无重启路径） |

**结论**：R-ark 同时消掉「合规」与「内核体积」两个结构性问题，且把「把 Node 塞进应用进程」这道题交给已验证的 `@fellow99/node-bridge`。代价是**放弃进程隔离**与**放弃 Chromium 的兼容性兜底** —— 这两个代价在 §12 里被显式登记，而不是被忽略。

### 2.2 opencode v2.0.26 的四个结构性事实（✅ 源码核实）

**(a) 服务化入口**：`opencode serve [--hostname|--port|--cors|--service|--stdio]`（`packages/cli/src/commands/commands.ts:539`）→ `ServerProcess.run({mode,hostname,port,cors})`（`packages/cli/src/commands/handlers/serve.ts`）→ `ServerProcess.start(options)`（`packages/cli/src/server-process.ts`）。`mode === "default"`（不带 `--service/--stdio`）时进程**常驻**（`Effect.never`）。

**(b) 密码必填**：`password` 缺失即失败（`packages/server/src/process.ts:52-53` `Missing server password`）。取值优先级：`--service` 模式读 service 配置或随机 → 否则 `OPENCODE_PASSWORD` / `OPENCODE_SERVER_PASSWORD` → 否则进程内随机 32 字节 base64url。

**(c) UI 与 API 同源托管**：`WebUi.handler()`（`packages/cli/src/services/web-ui.ts:20-36`）把 `/api`、`/api/*`、`/auth/*`、`/openapi.json` 交给 API，**其余路径全部走内嵌 UI**（未命中回落 `index.html`，SPA）。UI 资产是**内嵌 brotli 归档** `app-archive.bin`（`packages/cli/src/app-assets.ts`）；非 SEA 运行时从 `OPENCODE_NODE_ASSETS_DIR/app-archive.bin` 读取（`packages/cli/vite.node.config.ts` 的 `appAssetsPlugin`）。

⇒ **零前端工程、零自定义协议、零 preload 桥、零 CORS**：只要加载 `http://<host>:<port>/`，UI 与 API 就是同源。

**(d) 鉴权有三条通道**（`packages/server/src/middleware/authorization.ts`）：
1. `Authorization: Basic base64("opencode:<password>")`；
2. **URL 查询参数 `?auth_token=<base64("opencode:<password>")>`**（`credentialFromRequest` 读 `auth_token`）；
3. **会话 Cookie** `opencode_session_<port>`（HMAC 派生，30 天 TTL；`packages/server/src/auth.ts:38-58`），且**仅同源可用**（`origin` 与 `host` 必须一致，`middleware/authorization.ts` 的 `authorizedSessionCookie`）。

**(e) 前端原生支持「启动即带凭据」**：`packages/app/src/entry.tsx:81` 读取 `?auth_token=` → `authFromToken()` → 作为该 server 连接的 `password`；随后 `clearAuthToken()` 立刻把参数从地址栏抹掉。之后所有请求由 SDK 自动加 `Authorization: Basic …`（`packages/app/src/runtime/server/api.ts:5`）。

**这条 (e) 是本工程鉴权方案的地基**：不需要 Cookie API、不需要头改写、不需要 preload 注入，官方前端自己就会消费它。

### 2.3 运行时事实（`@fellow99/node-bridge`，✅/🔶 库文档）

| 事实 | 值 | 对本工程的要求 |
|---|---|---|
| Node 版本 / ABI | **v24.2.0** / `modules 137` / `soname libnode.so.137` | 上游产物必须按 **`node24`** 目标构建（§9 补丁 0001） |
| 平台标识 | `process.platform === 'openharmony'`、`arch === 'arm64'` | 任何 `platform === 'linux'` 分支都不会命中（`shell-select` 需要补丁，§9） |
| `dlopen` | 实测命中 `<bundleCodeDir>/libs/arm64/libnode.so`（设备 ABI 目录；库发布文档 §5.6，早期「只认裸名」口径作废） | 路径由库处理，宿主不管 |
| `node::Start` | **每进程一次**，无优雅停止 | 崩溃是终态；UI 必须给「请重启应用」 |
| `process.cwd()` | `/` | 启动脚本**必须显式 `chdir`** 到沙箱工作区（§5.6） |
| `process.execPath` | `/system/bin/appspawn` | 任何「用 execPath 重新拉起 Node」的代码必须改 |
| `os.cpus()` | 长度 **0** | 并发度探测类代码不能依赖它（⬜ 上游是否用到，Phase 0 验） |
| JIT | **需要 ACL**（`kernel.ALLOW_WRITABLE_CODE_MEMORY`）；无 ACL 即 SIGTRAP | ACL 是硬前置（§10） |
| `--jitless` | 可用，但 **WebAssembly 全废** | 不可作为兜底：undici 的 llhttp 是 WASM，fetch 会废 ⇒ 无法调模型 |
| `spawn` | 三事件齐全（`data`/`exit`/`close`），但**子进程 JIT 被 seccomp 拦**（SIGSYS，dsh ✅） | 只能 spawn 平台自带解释器/二进制，不能 spawn `node` |
| `flock` | 不支持 → 库视为成功 | 上游 `EffectFlock` 退化为进程内锁（⬜ 语义是否足够，Phase 1 验） |
| 宿主能力桥 | `HostBridge.register(name, handler)`，JSON 入出，可返回 Promise | 权限/选择器/外链/通知走这条（§6） |
| 日志 | stdout/stderr → 有界日志环 + `logs(count)`；`lastCrash()` | UI 的诊断面板直接消费 |

### 2.5 平台事实来源与两份互斥证据

**不重新论证**平台结论：JIT↔ACL↔WASM 链条、`spawn` 行为、symlink/hardlink/PTY/chmod/后台常驻等缺口，全部引用库文档（[fellow99/ohos-node-bridge](https://github.com/fellow99/ohos-node-bridge)）§4 / §D.8 与 `oc-desktop-hos/docs/鸿蒙环境能力清单-v2.0.26.md`。

**本工程必须自己裁决的冲突（⚠️）**：

| # | 一侧（🔶） | 另一侧（✅/🔶） | 本工程处置 |
|---|---|---|---|
| **X1 loopback** | `dsh-desktop-hos`：渲染进程访问 `127.0.0.1` 被**进程间网络隔离**拦截 → 必须绑 `0.0.0.0` + 局域网 IP 加载 | `pi-desktop-ark`：首选 loopback（同进程本地服务），并引「ArkWeb `loadUrl('http://127.0.0.1:5577')` 已在售应用」为证；⬜ 尚未自测 | **Phase 0 P0-D 专项探针**；两条路线都写进架构（§5.4），不做单点预设 |
| **X2 上架子进程/ELF** | 旧工程曾判「utility 进程可跑 Node」 | dsh：应用域 fork 出的 node 脚本 SIGSYS；桥：应用域执行自备 ELF 需二进制证书 | 本工程**不 spawn Node**，直接在应用进程内跑（§5.1），冲突不构成阻塞 |

## 3. 目标与原则

### 3.1 v1 目标（可逐条打勾）

1. **能起**：HAP 可安装、可启动，进入窗口，**无白屏、无闪退**；加载页 → 主界面有明确阶段文本。
2. **能对话**：完成「新建会话 → 发消息 → **流式**回复 → 工具调用可视化 → 重启应用后会话仍在」。
3. **能配模型**：Settings › Models 可填 API Key（凭据落沙箱），可切换 provider/model。
4. **能用工具**：文件读写/编辑/列目录/搜索（上游 `read`/`write`/`edit`/`glob`/`grep`/`list` 工具链）；`bash` 工具在可用 shell 下工作（降级策略见 §8.4）。
5. **能选工作区**：用户能在应用内选定工作目录并让服务端以该目录为项目根（§5.6）。
6. **能用 Git**（v1 新纳入）：搬 `oc-desktop-hos` 的 204 方案，diff/分支/提交在 UI 内可用。
7. **能上架**：主 UI 由 ArkWeb 渲染、**包内无浏览器内核**、ELF 合规、许可齐备、AI 标识常驻（§13）。
8. **失败可见**：任何一步失败都在 UI 上留下**可截图**的文字（阶段 + 原因 + 日志尾 + 「重启应用」提示），而不是白屏或静默。

### 3.2 设计原则

| 原则 | 展开 |
|---|---|
| **一切经 HTTP** | 前后端只通过同源 HTTP/SSE 通信；**不加 preload 桥、不引入 IPC 载体**（与 `pi-desktop-ark` 同口径） |
| **壳薄、契约硬** | ArkTS 只做「启动 / 观测 / 宿主能力 / 渲染」；业务全在 Node 侧 |
| **不改上游** | 优先用现成机制（`OPENCODE_*` 环境变量、条件变体、同名顶替）；补丁必须**幂等、可反向**（§9） |
| **不隐藏平台真相** | 终端不可用、搜索降级、git 走插件等如实上报，**不静默降级**（C2） |
| **判据可证伪** | 每条验收写成「能观测到 X」或「X 消失」；不用「看起来好了」 |
| **谁写谁读** | 需要 Node 读的文件由 Node 自己写；ArkTS 不解压业务文件（库 C3） |

## 5. 核心决策

> 决策登记：D1 运行时=bridge；D2 骨架=pi-desktop-ark；D3 服务端=stock CLI bundle；D4 端口=OS 分配 + stdout 嗅探 + marker；D5 渲染=ArkWeb；D6 网络=loopback 优先（探针裁决）；D7 鉴权=auth_token 优先；D8 密码=持久化；D9 载荷=resfile 直读优先；D10 SQLite=证据判定可用（零补丁）；D11 补丁=**本工程自有 `patches/v2.0.26/`**（0001/0003 必需、0006 待判）+ 基线守卫；D12 标识=OCDesktopArk；**D13 目录授权=沙箱 + 文档/下载 + 桌面（含 system_basic ACL）**；**D14 分发=按「要上架」设计、材料延后**；**D15 真机缺席期=先推进 host 侧（P0-A / P0-C host 半场 / 骨架）**。

### 5.1 运行时：进程内 Node（`@fellow99/node-bridge` + `@fellow99/node-runtime`，ohpm 双包）✅ 已确认

- **依赖形态**：以 **ohpm registry 双包**消费：`@fellow99/node-bridge@0.1.0`（接口与加载器）+ `@fellow99/node-runtime@24.2.0`（Node 引擎本体），版本在根 `oh-package.json5` **钉死**（不用 `*`）。**不直接用源目录**：跨工程相对路径导入在 `useNormalizedOHMUrl` 下被 hvigor 拒（`00309001`，🔶 pi-desktop-ark 踩坑）。
- **运行时引擎**：`libnode.so` / `libc++_shared.so` 由 `@fellow99/node-runtime` 包随 `assembleHap` 合并进 HAP（按路径去重一份）；宿主**不手工投放** `.so`，`entry/libs/` 不得放同名文件（两种来源择一）；构建期用 `scripts/verify-runtime.mjs` 校验包内 `libnode.so` 的 SHA-256/体积 = `runtime.lock.json` 锁值（不符硬失败）。
- **启动 API**：`NodeRuntime.getInstance().start(context, { scriptPath, env, flags, logPath })`；观测用 `logs(n)` / `lastCrash()` / `onStateChange`；停止用 `shutdown(reason)`（仅标记位，进程内无优雅退出）。
- **不新增第二个 Node 宿主**：不 fork、不 spawn、不用 `worker_threads` 再起一个 Node —— 进程内是唯一形态（`node::Start` 每进程一次）。

### 5.2 服务端：stock CLI bundle + `serve` 语义 ✅ 已确认

#### 5.2.1 产物

```bash
cd ../opencode
bun install --os=* --cpu=*
OPENCODE_NODE_TARGET=node24 bun run --cwd packages/cli script/build-node.ts \
  --target=linux-arm64 --bundle-only
# → packages/cli/dist-node/opencode.mjs + dist-node/assets/**（含 app-archive.bin）
```

- `--bundle-only`：**不产出 Node SEA**（SEA 需 Node 26.4.0 的 `--build-sea`，设备侧也不可能执行自备 ELF）。
- `--target=linux-arm64`：只是为了走通产物收集（原生件随后被裁掉/打桩）；**JS 部分是平台无关的**。
- `OPENCODE_NODE_TARGET=node24`：由补丁 0001 提供（把硬编码 `build.target: "node26"` 改为可注入），对齐 bridge 的 Node 24.2.0。
- **不新增上游构建脚本**（hos V2 已确立的口径）。

#### 5.2.2 宿主入口（`payload/opencode-server.js`）

职责固定为五步（**改写自 hos 的 `sidecar.js`**）：

1. 设 `process.env`（`OPENCODE_NODE_ASSETS_DIR` / `OPENCODE_PASSWORD` / `OPENCODE_DISABLE_*` / `XDG_*`，见 §5.6）；
2. `chdir` 到沙箱工作区（**必须在 import 之前**；否则服务端把项目根记成 `/`，`/api/fs/*` 直接 500，🔶 hos 真机结论）；
3. 安装 **stdout 嗅探**：包装 `process.stdout.write`，命中 `server listening on <url>` 时提取端口并写 `server.ready.json` + 打印 `ARK_SERVER_READY {"url":…,"port":…}`；
4. 设 `process.argv = ['node','opencode.mjs','serve','--hostname','127.0.0.1','--port','0']`；
5. `await import(pathToFileURL(entry))`；`catch` 里把 `stack` 写进独立日志（`<filesDir>/logs/server.log`）**且不 `process.exit`**（进程内 Node 的未捕获异常会把整个 App 带走，必须自己兜住）。

**投放位置**：本脚本随载荷投放 —— 路线 ① 放 `resfile/opencode/opencode-server.js`（只读直读），路线 ② 随 `tar.gz` 解到 `<filesDir>/opencode-dist/`；无论哪条，`scriptPath` 一律指向库的 `bootstrap.js`，本脚本由 `NODE_BRIDGE_ENTRY` 解析为**应用入口**（库文档 §5.5）。

**不覆盖库的日志通道**：库的 `bootstrap.js` 写 `<filesDir>/payload/app.log`；本脚本写 `<filesDir>/logs/server.log`。两者**不共文件**，否则「谁写谁读」的因果会被混流淹没（🔶 库 §D.10 ⑱）。

> **为什么端口用 `0`（OS 分配）而不是常量**：常量端口冲突会让 `listen()` 抛 `EADDRINUSE` → 进程内 Node 的未捕获异常 abort 整个 App（🔶 pi-desktop-ark 硬约束 ⑰ 真机实测）。`port 0` + 嗅探 + marker 是本工程唯一产品路径；常量端口只用于诊断。

### 5.4 网络：loopback 优先（⚠️ 冲突 X1，探针裁决）

| 路线 | 服务端 | ArkWeb URL | 前置 | 代价 |
|---|---|---|---|---|
| **A（首选）** | `--hostname 127.0.0.1` | `http://127.0.0.1:<port>/` | ArkWeb 能访问 loopback | 无；攻击面最小 |
| **B（回退）** | `--hostname 0.0.0.0` | `http://<局域网IP>:<port>/` | ArkTS 取本机非 internal IPv4（`@kit.NetworkKit` 的 `connection`） | 同网段可见（有密码 + 随机端口缓解）；非安全上下文可能影响 `crypto.subtle`/SW |

**裁决方式**：P0-D 一次探针 —— 在应用内起一个最小 HTTP 服务（bridge 的 `selfcheck` 即可），ArkWeb 加载并断言 `onPageEnd` + 页面内 `fetch('/')` 成功。**A 通过即锁定 A**；A 失败记录证据后切 B，并把结论回写本节。

**共同项**：`NO_PROXY`/`no_proxy` 追加 `127.0.0.1,localhost,::1,<LAN IP>`（避免代理拦截）；不启用 mDNS（v2 无 `--mdns`）；不写任何 Host/Origin 改写补丁（同源 + `origin` 与 `host` 天然一致）。

### 5.5 鉴权与凭据 ✅ 已确认（首选路线）

#### 5.5.1 三条通道与取舍

| 通道 | 做法 | 上游依据 | 结论 |
|---|---|---|---|
| **① `?auth_token=`（首选）** | ArkWeb 首次加载 `http://127.0.0.1:<port>/?auth_token=<btoa("opencode:"+PWD)>`；前端读取后**立即从地址栏抹掉**，并作为该连接的 `password` 持久化 | `packages/app/src/entry.tsx:81`、`runtime/server/api.ts:5`、`server/src/middleware/authorization.ts`（`auth_token` 查询参数） | ✅ **采用**：零 Cookie API、零头改写、零注入；后续请求由 SDK 自动加 Basic |
| **② 配对 Cookie** | Node 侧带 Basic `POST /api/pair` 取 `code` → ArkWeb 导航 `/auth/connect/<code>` → 服务端下发 `opencode_session_<port>` Cookie 并重定向 `/` | `packages/protocol/src/groups/server.ts:53-77`、`server/src/auth.ts:38-48` | 🔶 **保留为备选**：需要 ArkWeb Cookie 能力（`WebCookieManager`）或一次性导航；用于①被判定不可用的情形 |
| **③ Basic 注入** | 对每个请求注入 `Authorization` | — | ❌ 不采用：ArkWeb 无等价 `webRequest.onBeforeSendHeaders`；`onInterceptRequest` 全量代理成本过高 |

#### 5.5.2 为什么①成立（关键推理链）

1. 服务端**永远有密码**（§2.2b），三条通道都认；
2. 前端**原生**消费 `auth_token` 并落成 `ServerConnection.password`（`entry.tsx:81` + `registry.test.ts`「startup auth_token credentials override a persisted same-url server」）；
3. 该连接的**所有** API 调用由 SDK 加 Basic（`api.ts:5-31`），SSE 同理（`health.ts:106`）；
4. 因此 **ArkWeb 只需要一次正确的首屏导航**，之后不再依赖任何宿主注入能力。

#### 5.5.3 安全边界

- `auth_token` 会短暂出现在 URL 中 ⇒ **禁止把完整 URL 写进日志/诊断面板**（只记 `?auth_token=***`）；
- 服务端只监听 loopback（路线 A）⇒ 攻击面 = 同机其它应用；
- 若走路线 B（局域网），必须保留密码 + 随机端口，并在 UI 诊断面板显式提示「服务在本机局域网可达」。

#### 5.5.4 密码生命周期（`<filesDir>/ark/connection.json`，0600）

```json
{ "schema": 1, "password": "<32B base64url>", "createdAt": 0, "rotatedAt": 0 }
```

- **首次启动生成**，之后**复用**（跨启动稳定）——否则前端持久化的凭据会立刻过期，用户每次都要重新登录；
- 轮换只在「用户主动重置」或「文件损坏」时发生；
- 密码只经 `env` 交给 Node（`OPENCODE_PASSWORD`），**不写进任何日志**；`connection.json` 的读写在 ArkTS 侧完成（Node 不需要读它）。

| `OPENCODE_DB` | `<filesDir>/data/opencode/opencode.db` | 本工程 | 显式 DB 路径，免受 channel 文件名漂移影响（`database-path.ts`） |
| `OPENCODE_DISABLE_CHANNEL_DB` | `1` | 本工程 | 同上（channel 名来自分支名） |
| `OPENCODE_DISABLE_MODELS_FETCH` | `1` | 本工程 | 设备无外网依赖起步；models 已内嵌快照 |
| `OPENCODE_FILEWATCHER_DISABLE` | `1` | 本工程 | `@parcel/watcher` 无 ohos 构件 |
| `OPENCODE_DISABLE_FFF` | `1` | 本工程 | `fff` 需 Node FFI（Node 26 特性），设备不可用 |
| `OPENCODE_CLIENT` | `desktop` | 本工程 | 与上游 desktop 一致（写入 `app.name`） |
| `OPENCODE_LOG_LEVEL` | `info`（debug 构建可 `debug`） | 本工程 | 诊断 |
| `NO_PROXY` / `no_proxy` | `127.0.0.1,localhost,::1,<LAN IP>` | 本工程 | 避免代理拦截 |
| `PATH` | 前置 `/system/bin` | 本工程 | `bash` 工具要能找到 `sh`/`toybox` |

**补充（真机必需）**：`os.tmpdir()` 在 OHOS 上不读 `TMPDIR` ⇒ 若上游有 `os.tmpdir()` 依赖（`global-roots.ts` 的 `tmp`），必须在 bootstrap 里 **monkey-patch `os.tmpdir`** 指向 `<filesDir>/tmp`（🔶 hos 结论；⬜ 本工程复验）。

**cwd 规则**：`chdir(<filesDir>/workspace)`。opencode 的「项目」语义由**进程工作目录**决定（无 `--directory` 开关），cwd 是 `/` 会让 `/api/fs/*` 与建会话失败（🔶 hos 真机）。

## 9. 上游补丁策略

**纪律**（沿用 hos）：幂等判据 `git apply --reverse --check`；新补丁**不落在既有补丁上下文区间**（默认前后各 3 行）；追加到列表末尾；正反向往返须能 SHA-256 还原；换基线**新建** `patches/<新 tag>/`。

**补丁归属（D11，2026-10-18 决策）**：本工程**自带** `patches/v2.0.26/`，不与 `oc-desktop-hos` 共用目录；编号沿用 hos 的编号便于对照（**缺号 = 本工程不需要**）。因为 `../opencode` 是**两个工程共用**的 submodule，`scripts/apply-patches.mjs` 增加**基线守卫**：

1. HEAD 必须是锁定基线 `9b4ec5714d`（`EXPECTED_BASELINE` 可覆盖）；
2. 工作树必须干净（`git status --porcelain` 为空）——否则「另一个工程留下的脏树」会被误判成「本工程已打补丁」；
3. 确实要丢弃本地改动时显式 `--reset --yes`（先 `git clean -nd` 打印将删除项）；
4. 应用后必须 `--reverse --check` 通过，**不留半应用状态**。

## 10. ACL 与权限

### 10.1 声明面（Phase 1 定稿，当前为设计基线）

落点：`entry/src/main/module.json5`（单模块应用）。

| 类别 | 项 | 说明 |
|---|---|---|
| 开放权限 | `ohos.permission.INTERNET`、`GET_NETWORK_INFO`、`KEEP_BACKGROUND_RUNNING` | 本机 HTTP 服务 + 网络信息 + `backgroundModes:["taskKeeping"]` |
| 受限权限（**ACL**） | `ohos.permission.kernel.ALLOW_WRITABLE_CODE_MEMORY` | **JIT 硬前置**：无它 V8 走 JIT 即 SIGTRAP，属应用级失败 |
| 受限权限（**ACL**） | `ohos.permission.READ_PASTEBOARD` | 剪贴板粘贴到输入框 |
| 受限权限（**ACL**） | `ohos.permission.READ_WRITE_DESKTOP_DIRECTORY` | 工作区位于桌面目录时直写。**✅ D13 已确认 v1 就申请**（申请周期最长项，材料需提前备） |
| 用户授权 | `READ_WRITE_DOCUMENTS_DIRECTORY`、`READ_WRITE_DOWNLOAD_DIRECTORY` | 目录选择器授权后可用 |
| `definePermissions` | `kernel.ALLOW_WRITABLE_CODE_MEMORY` | 与 `requestPermissions` **成对出现**（缺一不可） |

> 与 `pi-desktop-ark` 的 24 项不同：那 24 项是**为对齐 Electron 的 `web_engine` 声明面**而逐项复制的（相机/麦克风/蓝牙等本工程用不到）。本工程按**真实需要**申报，并在 Phase 1 用脚本比对「声明面 = 使用面」，多一项都要写理由。

### 10.2 三条硬规则（真机教训）

1. **声明面 ≠ 授权面**：Profile 不含 ACL 时 `hdc install` 直接失败（`9568289 / PermissionName: …`）。改 Profile → 重新签名 → 重装。
2. **ACL 按包名申请**：`org.fellow99.oc.OCDesktopArk` 必须独立申请，不能复用 hos 版。
3. **无 ACL 时不要试图用 `--jitless` 蒙混**：WASM 全废 ⇒ undici（llhttp）废 ⇒ 模型请求废 ⇒ 产品不可用。

### 10.3 验收判据（可证伪）

① 真机**不带** `--jitless` 启动内嵌 Node → **无** `Cpp Crash` / SIGTRAP；
② 服务端 `/api/info` 200；③ 一次真实对话成功（含流式）；
④ 粘贴图片/文本进输入框可用（`READ_PASTEBOARD` 生效）。
